# 搜索策略：如何找到合适的现成方案

接到开发任务后，按以下顺序搜索与筛选。

## 一、搜索渠道（按优先级）

1. **GitHub 搜索**：关键词 + 功能描述，按 star 数排序；`site:github.com` 亦可用于通用搜索。
2. **包管理器**：npm / PyPI / Maven / cargo 等，优先可安装为依赖的包。
3. **awesome 列表**：搜索 `awesome <领域>`，通常收录了该领域最成熟的项目。
4. **技术社区**：Stack Overflow、V2EX、掘金、Hacker News，寻找经过验证的推荐。

## 二、关键词技巧

- 用功能词而非实现词搜索：要「markdown 转 docx」就搜 `markdown docx converter`，而不是自建方案的名称。
- 中英文各搜一遍。
- 换同义词再搜：`pagination` / `page numbers` / `分页`。

## 三、候选评估标准

| 维度 | 检查点 |
|------|--------|
| 成熟度 | star 数、issue 活跃度、最近提交时间（建议一年内有维护） |
| 质量 | 有无测试、CI、文档；代码是否清晰 |
| 许可证 | MIT / Apache-2.0 / BSD 可放心用；GPL 注意传染性；无许可证 = 默认保留所有权利，不可直接复用 |
| 依赖 | 依赖数量与是否仍被维护，避免引入被废弃的链条 |
| 兼容性 | 语言/框架版本、平台、与当前项目技术栈是否匹配 |

## 四、决策顺序

1. **可直接作为依赖引入** → 直接复用。
2. **不能直接用，但代码可修** → fork / 内嵌，修复后使用（能修就不重写）。
3. **需要适配业务** → 改造集成（能改就不重造）。
4. **搜索多轮（含不同关键词、不同渠道）后确认无合适方案** → 才允许从零开发，并说明理由。
